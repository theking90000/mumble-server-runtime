# Establishing compatibility

An implementation cannot certify itself. A test written from the same
understanding that produced a defect agrees with the defect.

Seven mechanisms judge this runtime, ordered below by increasing distance from
the code they judge. Each one is independent of it, and the last section states
what none of them proves.

## The upstream sources

Protocol facts come from the Mumble project's own sources, pinned at one commit
and kept in the repository alongside the extracts they were taken from. The
protobuf schema is compiled from those files when the workspace builds, and is
never transcribed by hand.

Every module asserting a protocol fact carries a comment naming the upstream
file it came from. Those comments are a convention, not a machine check: nothing
verifies that one is still accurate. This is the weakest link in the chain.

The one place upstream truth is executed rather than cited is the encryption
layer, which is checked against the published test vectors for the cipher it
implements.

## The recorded corpus

Seven sessions between an official Mumble client and a real reference server
were captured through a proxy that logs and decodes nothing, and are kept in the
repository: a handshake, channel entry and exit, channel creation and removal,
two clients talking, a whisper, a refusal, and a disconnection.

Replaying them proves three things at once. Every byte of every stream is
accounted for, so nothing is skipped as unrecognised. Every decoded message
re-encodes to the bytes that were captured, so the codec is a fixed point on
real traffic. And a capture from an older server, whose voice format is
deliberately out of scope, must still be rejected rather than misparsed.

Capturing a scenario requires driving a graphical client by hand, which is why
the corpus grows slowly.

## The intermediate proxy

A proxy sits between a real client and a real reference server, terminating the
connection on both sides, decoding and re-encoding every control message in
flight, and rewriting the key exchange so it holds an independent cipher domain
toward each side.

The codec therefore meets live traffic it did not produce, generated by an
implementation that knows nothing about it. A message that survives the round
trip unchanged has been read correctly by definition.

## The simulated client

A simulated client applies every server message to a strict model of what a
client believes, and refuses any state the official client would reject. It is
written against the specification and the upstream sources, never against this
server.

What it refuses:

- a channel whose parent is not visible,
- a participant placed in a channel that is not visible,
- a cycle in the channel tree,
- the removal of an occupied channel, or of a parent before its children,
- the removal of the root,
- any message referencing a channel or a session the client cannot see,
- an identifier reused after being retired,
- synchronisation before the connection has been introduced to itself.

Each rule is a separate named check, so deleting one is visible rather than
absorbed by another. A table-driven test feeds an invisible identifier into
every field of every message that carries one, and requires each to be caught.

## The publication oracle

The simulated client is also used as the right-hand side of an equality checked
after every message a shard sends:

```text
  what the client believes  ==  the scoped shared view  +  its private overlay
```

Two choices in that sentence carry the weight.

The model is fed the encoded control messages rather than the internal plan, so
the translation between the two is inside the property rather than trusted.

The check runs after every message rather than at the end of a transition. An
ordering defect produces a transiently invalid state and a perfectly correct
final one, so a comparison of endpoints cannot see it.

The generator interleaves four classes of change at random: shared content, an
element moving between scopes, the observing connection moving between scopes,
and a private overlay appearing or disappearing. It asserts its own coverage,
because a generator that quietly stops exercising a class is worse than none.

Three tests then compose the pipeline wrongly on purpose and require the
property to fail. If one of them ever passes, the generator has gone weak rather
than the code correct.

## Live sockets

The end-to-end suite opens real TLS connections and real datagrams against a
server bound on a loopback port. No transport is mocked, and no test sleeps to
wait for state: a test advances when the server has actually said something.

It covers what a client experiences rather than what a function returns: two
clients hearing each other over UDP, a client that never opens UDP served
through the tunnel, a one-way listener, two connections given different trees, a
migration that does not remove a client from its own view, mute and deafen, menu
entries, text scope, and refusals.

## Fuzzing

The decoders are required to return on arbitrary bytes, never to panic, and to
fail closed rather than accept something they did not understand. Round-tripping
a decoded message is required to be a fixed point at the byte level, which is
the property the intermediate proxy depends on.

A short run over every target is a script; a deterministic equivalent runs on
every build so the property is checked even without the tooling.

## Separation

A change may not touch a judge and the implementation it judges in the same
revision. Loosening a model, editing a captured session or weakening a check is
legitimate only as its own reviewed change, never as a side effect of making
something pass.

## What none of this proves

The list matters as much as the mechanisms.

Rules a client cannot observe are out of reach. A model built from what arrives
on the wire can only judge what arrives on the wire.

The strict model knows structure and identity: channels, participants, parents,
names, sessions. It does not model permissions, positions, flags, comments or
links, so a defect confined to those fields passes it.

Three deliberately wrong pipelines are three known classes of defect, not a
mutation score. They show the property is sensitive to those three, and say
nothing about the rest.

The corpus has no capture of an encryption resynchronisation and none of an
older client, which are the two cases most likely to behave unexpectedly.

Official clients were used throughout development, and that is a person
watching, not a machine checking. It catches what a person notices.

## Running them

```sh
# everything below, and the rest
cargo test --workspace

cargo test -p mumble-server-runtime-corpus-decode          # the corpus
cargo test -p mumble-server-runtime-mitm-proxy             # the proxy, offline
cargo test -p mumble-server-runtime-testkit                # the simulated client
cargo test -p mumble-server-runtime-shard --test oracle    # the oracle
cargo test -p mumble-server-runtime-gateway --test gateway # real sockets
ci/fuzz-smoke.sh                                           # every fuzz target
```

The proxy is also a program. Pointing a real client at it, with a reference
server upstream, is the observation the offline tests stand in for:

```sh
cargo run -p mumble-server-runtime-mitm-proxy -- \
    --listen 0.0.0.0:64738 --upstream 127.0.0.1:64739 --tls-name localhost
```
